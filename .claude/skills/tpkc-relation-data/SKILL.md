# TPKC 關係鏈資料

## 用意（先懂這個，再動手）

終極目標：**任何設備發生事情，都能追查到影響哪些客戶**。資料要能正查（設備 → 客戶）也能反查（客戶 → 設備）。
圖 = 節點 + 有方向的邊。**邊的方向 = 影響的方向**（電源 → 負載 → … → 客戶）。沿方向走不到客戶的節點代表關係鏈有缺口；連不到根節點 `TPKC 大樓` 的節點是「未處理」。
規格：`/Users/cain/01_fet/tpkc/tpkc-pd-docs/docs/需求與設計/節點編輯器/PRD.md`（§3 定義、§5 資料）。

## 名詞與類型文檔（按需載入，不要一開始全讀）

| 讀這份                   | 什麼時候                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| `references/glossary.md` | 遇到不確定的名詞（key、通用節點、未處理、無客戶路徑、確認狀態…）或要判斷「這該不該成節點」 |
| `references/types.md`    | 要決定來源的東西是哪個節點類型、該用哪種邊、方向對不對，或來源對不上現有類型               |

## 資料結構（單一事實來源是程式，不要抄進這裡）

- 系統、節點類型、邊類型與連接限制：`src/lib/model/config.ts`
- CSV 格式與驗證：`src/lib/model/csv.ts`（`buildGraph`）；連接限制檢查：`src/lib/model/graph.ts` 的 `validateEdge`
- 範例：`static/data/`（`index.json` 列出所有檔）

重點：

- 節點 `key`：必填、全圖唯一（含 IDC）、建立後不可改，邊用 key 當起點／終點。`名稱` 選填，空白顯示 key。
- 節點檔 `nodes/<系統>.csv`，每列自帶 `類型`；`通用` 檔是不屬於任何系統的節點。邊檔 `edges/<邊類型>.csv`：`起點,終點,雙向,確認狀態`（供電多一欄 `路別`）。
- `確認狀態`：`已確認`＝有來源佐證；`推定`＝推論。拿不準就填 `推定`。
- `idc/` 底下（機框、主機、客戶與其邊）由 IDC 系統維護，視為唯讀來源。

## 鐵則

1. **來源資料與 `static/data/` 一律唯讀**。輸出只寫 `data-staging/`（同樣結構，含 `index.json`）。要切到 `static/data/` 必須使用者明說。
2. **不編造**。資料沒寫的 key、關係、方向都不補。不確定 → 列進「待確認」問使用者，或標 `推定`。
3. **不新增類型**。對不上現有類型 → 列為待確認；新增類型要改 `config.ts`（程式變更），先問。
4. **合併，不覆蓋**。`data-staging/` 已有資料時，依 key（節點）與 起點>終點（邊）合併；與既有列衝突就停下來問，不默默覆蓋。

## 流程（每次餵資料跑一輪）

1. **讀記憶**：`memory/` 三個檔全讀（見下）。名詞文檔按上表需要才讀。
2. **讀來源**：任何形式都行。先說你看到什麼、打算怎麼對應。
3. **對應**：先依 `memory/mapping.md`；沒有現成對照的，讀 `references/types.md` 判斷類型與邊；仍對不上列「待確認」。
4. **寫 `data-staging/`**：節點、邊、`index.json`。
5. **驗證**：`DATA_DIR=data-staging pnpm vitest run scripts/validate-data.test.ts`。錯誤（key 重複、端點不存在、連接限制）必須清零；「未處理」「無客戶路徑」數量只回報，缺口多半是資料還沒餵齊。
6. **回報**：新增／變更／衝突／待確認／驗證結果，各一段，短。
7. **回寫記憶**（見下）。

## 記憶（讓技能自己長大）

`memory/` 都進版控，下輪由下一個 agent 讀到：

| 檔             | 放什麼                                | 何時寫                     |
| -------------- | ------------------------------------- | -------------------------- |
| `mapping.md`   | 來源詞彙／欄位 → 類型、邊、屬性的對照 | 驗證通過且使用者沒反對才寫 |
| `decisions.md` | 使用者拍板的規則（含日期、原話要點）  | 只在使用者明確裁示後寫     |
| `lessons.md`   | 踩過的坑、來源的怪癖、驗證抓到的錯    | 每輪有新發現就寫           |

寫法：只加不改歷史；一條一行；與舊條目矛盾時，在舊條目後標「已被 YYYY-MM-DD 取代」並新增。每輪結束前問自己：這輪學到什麼，下個 agent 不讀會再犯？
記憶的更新與資料一起提交。
