# TPKC 關係鏈資料

## 用意（先懂這個，再動手）

終極目標：**任何設備發生事情，都能追查到影響哪些客戶**。資料要能正查（設備 → 客戶）也能反查（客戶 → 設備）。
圖 = 節點 + 有方向的邊。**邊的方向 = 影響的方向**（電源 → 負載 → … → 客戶）。沿方向走不到客戶的節點代表關係鏈有缺口；連不到根節點 `TPKC 大樓` 的節點是「未處理」。
規格：`/Users/cain/01_fet/tpkc/tpkc-pd-docs/docs/需求與設計/節點編輯器/PRD.md`（§3 定義、§5 資料）。

## 名詞與類型文檔（按需載入，不要一開始全讀）

| 讀這份                   | 什麼時候                                                                                   |
| ------------------------ | ------------------------------------------------------------------------------------------ |
| `references/glossary.md` | 遇到不確定的名詞（key、通用節點、未處理、無客戶路徑、確認狀態…）或要判斷「這該不該成節點」 |
| `references/types.md`    | 要決定來源的東西是哪個節點類型、該用哪種邊、方向對不對，或來源對不上現有類型               |

## 資料結構（單一事實來源是程式，不要抄進這裡）

- 系統、節點類型、邊類型與連接限制：`src/lib/model/config.ts`
- CSV 格式與驗證：`src/lib/model/csv.ts`（`buildGraph`）；連接限制檢查：`src/lib/model/graph.ts` 的 `validateEdge`
- 範例：`static/data/`（`index.json` 列出所有檔）

重點：

- 節點 `key`：必填、全圖唯一（含 IDC）、建立後不可改，邊用 key 當起點／終點。`名稱` 選填，空白顯示 key。
- 節點檔 `nodes/<系統>.csv`，每列自帶 `類型`；`通用` 檔是不屬於任何系統的節點。邊檔 `edges/<邊類型>.csv`：`起點,終點,雙向,確認狀態`（供電多一欄 `路別`）。
- `確認狀態`：`已確認`＝有來源佐證；`推定`＝推論。拿不準就填 `推定`。
- `idc/` 底下（機框、主機、客戶與其邊）**本技能不編輯**（使用者另外維護）；只當邊的端點用，繼承版本時原樣複製。

## 鐵則

1. **來源資料與 `static/data/` 一律唯讀**。產出是**新版本**：`data-staging/` 是一份完整、可直接載入的資料夾（同樣結構，含 `index.json`），使用者在 app 用「選資料夾」指向它就生效。歷史靠 git。
2. **不編造**。資料沒寫的 key、關係、方向都不補。不確定 → 列進「待確認」問使用者，或標 `推定`。
3. **不新增類型**。對不上現有類型 → 列為待確認；新增類型要改 `config.ts`（程式變更），先問。
4. **合併，不覆蓋**。`data-staging/` 已有資料時，依 key（節點）與 起點>終點（邊）合併；與既有列衝突就停下來問，不默默覆蓋。

## 流程（workflow，每次餵資料跑一輪）

主 agent 是**協調者**：只推進流程、派 subagent、問使用者、回寫記憶，不自己抽取或對應。每個角色的派工內容在 `roles/`，派工時把該檔全文與輸入一起交給 subagent。中間產物放 `data-staging/_work/`（進版控），中斷時從這裡接手。

```
使用者資料 → ①抽取員×N（並行）→ ②對應員 ⇄ ③審查員 → ④寫入員 → ⑤驗證 → 回報
                                    ▲ 退回／驗證失敗 ┘
```

0. **讀記憶與定基底**：`memory/` 三個檔全讀。問使用者這輪要繼承哪個版本（目前的 `data-staging/`、`static/data/`）或從空白開始；繼承 `static/data/` 就整份複製（含 `idc/`）進 `data-staging/`，空白就只建 `index.json`。
1. **抽取**：每份來源派一個 `roles/extractor.md`，並行 → `_work/facts/`。口語描述也當一份來源。
2. **對應**：派 `roles/mapper.md` → `_work/changeset.md`。
3. **審查**：另派 `roles/reviewer.md`（不同 subagent）→ `_work/review.md`。退回 → 帶理由回到 2。
4. **問使用者**：changeset 的「衝突」「疑似同物異名」「待確認」與審查員補的問題，整理成問題清單（互相牽動的排前面），然後**一次只問一題**。每題：
   - **白話**：不用 key、檔名、行號、類型術語當主詞；講「哪台設備、接到哪」。
   - **說明疑惑原因**：你說了什麼、資料裡現在是什麼、兩者哪裡對不上。
   - **給選項**：(甲)(乙)…，每個選項寫選了會發生什麼（改不改資料、影響多大）；最後標「建議選 X」與一句理由。
   - 回答後先用一兩句複述理解，再問下一題；已被前面答案解決的題目，說明原因後跳過。
   - 全部答完回到 2；使用者說「先標推定」的照辦。
5. **寫入**：審查通過、問題都有答案後派 `roles/writer.md`。
6. **驗證**：`DATA_DIR=data-staging pnpm vitest run scripts/validate-data.test.ts`，錯誤必須清零（失敗回到 2）；「未處理」「無客戶路徑」數量只回報。再請審查員看一次 `git diff data-staging/`。
7. **回報**：新增／變更／衝突／待確認／驗證結果，各一段，短。提醒使用者在 app 選 `data-staging/` 檢查。
8. **回寫記憶**（見下），與資料、`_work/` 一起提交；提交後清掉 `_work/` 這輪的檔（歷史留在 git）。

**結束條件**：審查員零退回、驗證零錯誤、問題都已回答或使用者明示先標推定。

## 記憶（讓技能自己長大）

`memory/` 都進版控，下輪由下一個 agent 讀到：

| 檔             | 放什麼                                | 何時寫                     |
| -------------- | ------------------------------------- | -------------------------- |
| `mapping.md`   | 來源詞彙／欄位 → 類型、邊、屬性的對照 | 驗證通過且使用者沒反對才寫 |
| `decisions.md` | 使用者拍板的規則（含日期、原話要點）  | 只在使用者明確裁示後寫     |
| `lessons.md`   | 踩過的坑、來源的怪癖、驗證抓到的錯    | 每輪有新發現就寫           |

寫法：只加不改歷史；一條一行；與舊條目矛盾時，在舊條目後標「已被 YYYY-MM-DD 取代」並新增。每輪結束前問自己：這輪學到什麼，下個 agent 不讀會再犯？
記憶的更新與資料一起提交。
